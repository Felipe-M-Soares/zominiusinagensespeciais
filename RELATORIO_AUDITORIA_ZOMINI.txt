[CRÍTICO-01] ESTOQUE INTERMEDIÁRIO MOSTRANDO APENAS 500 DE 5133 ITENS
──────────────────────────────────────────────────────────────────────
Gravidade   : CRÍTICO
Prioridade  : IMEDIATA
Arquivo     : supabase/migrations/20260019000000_performance_stock_load.sql
              src/hooks/useStock.ts

Problema:
  A função load_stock_page tem LEAST(COALESCE(p_limit, 200), 500) que clampeia
  em 500 registros no servidor, independente do que o cliente solicite. Com
  5133 itens no intermediário, 4633 ficavam invisíveis. O cliente enviava
  p_limit: 500 — o teto era 500 — resultando em 500 exibidos.

Impacto:
  Operadores não visualizavam 90% do estoque. Vendas e transferências poderiam
  referenciar itens "inexistentes" para o sistema.

Correção aplicada (migration 20260603000000_fix_stock_limit.sql):
  - LEAST(p_limit, 500) → LEAST(p_limit, 10000)
  - Quando p_device_ids IS NOT NULL (busca direcionada): LIMIT removido
  - Cliente atualizado: p_limit: 500 → p_limit: 10000
  Status: CORRIGIDO ✓


[CRÍTICO-02] BUSCA NA BARRA DE PESQUISA SÓ RETORNAVA RESULTADOS DA 1ª PÁGINA
─────────────────────────────────────────────────────────────────────────────
Gravidade   : CRÍTICO
Prioridade  : IMEDIATA
Arquivo     : src/pages/Estoque.tsx

Problema:
  Ao pesquisar, visibleCount era resetado para ITEMS_PER_PAGE (60) e o display
  usava filteredItems.slice(0, visibleCount) — exibindo apenas os primeiros 60
  resultados filtrados. Se os itens pesquisados estivessem nas posições 61-5133,

  const pagedItems = hasSearch ? filteredItems : filteredItems.slice(0, visibleCount);
  Status: CORRIGIDO ✓

[SEG-01] SENHA PADRÃO DE ADMIN HARDCODED NA MIGRATION — RISCO ALTO

[SEG-02] verify_jwt = false EM TODAS AS EDGE FUNCTIONS
──────────────────────────────────────────────────────
Gravidade   : MÉDIO-ALTO
Prioridade  : ALTA
Arquivo     : supabase/config.toml

Problema:
  Todas as 6 Edge Functions têm verify_jwt = false no config.toml. Isso
  desabilita a verificação automática de JWT pelo gateway do Supabase, delegando
  100% da responsabilidade de autenticação para cada função individualmente.
  Uma função com bug no JWT parsing (edge case, biblioteca desatualizada) se
  torna imediatamente explorável sem camada de proteção adicional.

  Funções afetadas:
    - admin-create-user   (operação crítica de admin)
    - admin-reset-password (operação crítica de admin)
    - delete-account      (operação destrutiva)
    - import-devices      (importação em massa)
    - auto-approve
    - auth-email-hook     (JUSTIFICÁVEL: hooks de auth precisam verify_jwt=false)

Recomendação:
  Habilitar verify_jwt = true para admin-create-user e admin-reset-password.
  Manter false APENAS para auth-email-hook (que recebe chamadas do sistema auth).
  Status: NÃO CORRIGIDO — recomendado


[SEG-03] CSP COM unsafe-inline — XSS PARCIALMENTE MITIGADO
──────────────────────────────────────────────────────────
Gravidade   : MÉDIO
Prioridade  : MÉDIA
Arquivo     : vercel.json

Problema:
  Content-Security-Policy contém 'unsafe-inline' em script-src e style-src.
  Isso permite execução de scripts inline no documento HTML, enfraquecendo
  a proteção XSS. O Vite/React necessita de inline styles mas não de inline
  scripts em produção.

  Linha atual:
    "script-src 'self' 'unsafe-inline' blob:;"

Impacto:
  Um atacante com capacidade de injetar HTML (ex: via dados do banco exibidos
  sem escHtml) pode executar JavaScript inline.

Nota positiva:
  O projeto usa escHtml() consistentemente em templates de impressão. Mas
  outros locais (ex: React dangerouslySetInnerHTML) não foram encontrados,
  o que é bom.

Recomendação:
  Usar nonce ou hash para scripts inline necessários. Para Vite, usar
  vite-plugin-csp ou configurar nonce via plugin.
  Status: NÃO CORRIGIDO — recomendado


[SEG-04] RATE LIMITING IN-MEMORY INEFICAZ (EDGE FUNCTIONS STATELESS)
─────────────────────────────────────────────────────────────────────
Gravidade   : MÉDIO
Prioridade  : MÉDIA
Arquivo     : supabase/functions/admin-create-user/index.ts (linha 16)

Problema:
  const rateLimitMap = new Map<string, { count: number; resetAt: number }>();
  Deno Edge Functions são stateless e podem ter múltiplas instâncias simultâneas.
  O Map em memória é descartado a cada cold start e não é compartilhado entre
  instâncias — um atacante pode contornar o rate limit simplesmente esperando
  o cold start ou usando múltiplas conexões simultâneas.

Impacto:
  Rate limiting para criação de usuários admin pode ser burlado.

Recomendação:
  Usar o sistema check_rate_limit já implementado no banco (migration 017).
  A Edge Function deve chamar check_rate_limit('admin_create_user') antes
  de processar. O banco é o único state compartilhado entre instâncias.
  Status: NÃO CORRIGIDO — recomendado


[SEG-05] FUNÇÕES SQL SECURITY DEFINER SEM SET search_path (migration 20260531)
──────────────────────────────────────────────────────────────────────────────
Gravidade   : MÉDIO
Prioridade  : MÉDIA
Arquivo     : supabase/migrations/20260531_performance_functions.sql

Recomendação:

    SET search_path = public;
  Adicionar: IF auth.uid() IS NULL THEN RETURN 0; END IF;
  Status: NÃO CORRIGIDO — recomendado

[SEG-08] reserve_stock SILENCIA OVERFLOW DE RESERVA
─────────────────────────────────────────────────────
Gravidade   : MÉDIO
Prioridade  : MÉDIA
Arquivo     : supabase/migrations/20260016000000_security_rpc_guards.sql

Problema:
  SET quantity_reserved = LEAST(quantity, quantity_reserved + v_qty)
  Se tentar reservar mais do que o disponível, o sistema reserva o que tiver
  silenciosamente sem retornar erro. Isso pode causar:
  - Pedidos confirmados com menos unidades do que o solicitado
  - Inconsistência entre o que o cliente acredita ter reservado e o real

Recomendação:
  Verificar disponibilidade antes de reservar e retornar erro explícito:
    IF (quantity - quantity_reserved) < v_qty THEN
      RETURN jsonb_build_object('ok', false, 'error', 'Estoque insuficiente');
    END IF;
  Status: NÃO CORRIGIDO — recomendado

[PERF-02] CLEANUP DO TRIGGER DE RATE LIMIT RODA A CADA INSERT
──────────────────────────────────────────────────────────────
Gravidade   : BAIXO
Prioridade  : BAIXA
Arquivo     : supabase/migrations/20260017000000_ddos_rate_limiting.sql

Problema:
  O trigger trg_cleanup_rate_limit executa DELETE de entradas antigas em
  CADA INSERT na tabela rate_limit_log. Em picos de uso isso causa lock
  contention na tabela.

  ou usar pg_cron para cleanup periódico:

    BEGIN
      IF random() < 0.01 THEN  -- cleanup 1% das vezes
        DELETE FROM public.rate_limit_log WHERE created_at < now() - interval '5 minutes';
      END IF;
      RETURN NULL;
    END; $$ LANGUAGE plpgsql ...
  Status: NÃO CORRIGIDO — baixa prioridade
